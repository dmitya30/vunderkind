# Инструкции для AI-агентов

Обязательные правила работы с проектом **vunderkind**.

## 1. Источники истины

Приоритет источников:

1. Живой сайт `https://supermozg.pro/` — источник истины по опубликованному
   контенту, ценам, программам, контактам, отзывам и утверждённым заказчицей
   формулировкам.
2. Актуальный код ветки `main` — источник истины по реализации.
3. `docs/PROJECT.md` — компактный контекст проекта, статус и ожидающие задачи.
4. История Git — источник удалённых и устаревших материалов.

Документы из истории разработки не должны автоматически использоваться для
изменения production-контента. Репозиторий заказчица не проверяла, а сайт был
прочитан и исправлен заказчицей.

Контент production-сайта нельзя менять без прямого задания пользователя.
Допустимы технические исправления HTML, CSS и JavaScript, не меняющие
утверждённый смысл и фактические данные.

## 2. Экономное восстановление контекста

Преимущественно использовать уже имеющиеся данные текущего диалога.

Не перечитывать сеть, production и одни и те же файлы перед каждым ответом.
Повторные обращения создают дублирование, расходуют токены и лимиты и повышают
риск сжатия диалога.

Обращаться к сети или репозиторию, когда:

- пользователь прямо просит проверить актуальное состояние;
- контекст был сжат или потерян;
- данные могли измениться;
- без проверки нельзя безопасно выполнить задачу;
- требуется верификация результата после push/deploy.

После подтверждённого сжатия контекста:

1. прочитать `AGENTS.md`;
2. прочитать `docs/PROJECT.md`;
3. проверить только файлы, относящиеся к текущей задаче;
4. проверять production и последние коммиты только при реальной необходимости.

Не загружать повторно большие файлы, если их актуальное содержимое уже есть в
диалоге и не менялось.

## 3. Рабочая среда

```text
Git Bash / MINGW64, Windows 10
Корень: ~/projects/vunderkind
```

Правила:

- только команды Git Bash;
- не использовать PowerShell и cmd;
- каждый исполняемый блок начинать с
  `cd ~/projects/vunderkind &&`;
- не предполагать текущую директорию;
- использовать пути с `/`;
- Python всегда читает и пишет текст с `encoding='utf-8'`;
- цепочки команд строить через `&&`;
- не использовать `set -e`, `set -E`, `set -u`, `set -o pipefail`,
  `exit` и `exit 1` в интерактивных блоках;
- потенциально неуспешные проверки оформлять через `if`, `&&` или `|| true`.

## 4. Порядок изменений

Перед изменениями:

1. проверить `git status --short`;
2. прочитать только затрагиваемые файлы;
3. определить минимальный безопасный патч.

После изменений:

1. проверить `git diff --check`;
2. проверить синтаксис изменённых файлов доступными инструментами;
3. проверить `git diff`;
4. убедиться, что контент сайта не изменён без задания;
5. сделать commit с понятным сообщением;
6. push в `main`;
7. проверить GitHub Actions и production, если менялся сайт.

Не переписывать большие файлы без необходимости. Не выполнять массовые
форматирования вместе с функциональным исправлением.

## 5. Контент

- Production-сайт — текущая утверждённая версия контента.
- Не исправлять цены, подписи отзывов, часы работы, программы и контакты на
  основании старых файлов документации.
- Не сокращать и не переписывать отзывы без прямого задания.
- Не добавлять факты, которых нет на production или в сообщении пользователя.
- Имена педагогов допустимы внутри уже утверждённых отзывов.
- Основной рекламный текст остаётся без персонализации под конкретного тренера.
- Формы сбора персональных данных нет.
- Все CTA открывают контактную модалку; текстовые телефонные ссылки остаются
  прямыми `tel:`.

## 6. Технические ориентиры

- Статический одностраничный сайт: HTML, CSS, vanilla JavaScript.
- Хостинг: GitHub Pages.
- Деплой: `.github/workflows/deploy.yml` при push в `main`.
- Production: `https://supermozg.pro/`.
- Основные файлы: `index.html`, `style.css`, `script.js`.
- Метрика должна оставаться в конце `body`.
- Сайт должен работать без сборщика и серверной части.
- Проверять desktop, tablet и mobile.
- Интерактивные элементы должны работать с клавиатуры.
- Модалки должны управлять фокусом и закрываться по Escape.

## 7. Документация

Активная документация намеренно сведена к двум файлам:

- `AGENTS.md` — правила работы;
- `docs/PROJECT.md` — состояние проекта и задачи.

Не создавать отдельный документ для каждого этапа. Новую актуальную информацию
добавлять в один из этих двух файлов. Устаревшие материалы доступны через Git.

## 8. Коммуникация

Не задавать вопросы, если ответ уже есть в диалоге или актуальной документации.
Если данных не хватает, выполнить все неблокируемые действия и задать только
конкретный блокирующий вопрос.

Исправления пользователя имеют приоритет над прежними предположениями.
После существенного уточнения обновлять `docs/PROJECT.md`.
