# Инструкции для AI-агентов

Этот файл содержит обязательные правила работы с репозиторием vunderkind.

## Восстановление контекста

После сжатия или потери диалога необходимо:

1. прочитать `AGENTS.md`;
2. прочитать `docs/PROGRESS.md`;
3. прочитать `docs/PROJECT.md`;
4. проверить последние коммиты через GitHub API;
5. проверить актуальные файлы `index.html`, `style.css`, `script.js`;
6. только после этого предлагать или вносить изменения.

Пользователь подскажет, когда произошло сжатие диалога. После такого сообщения чтение `AGENTS.md` обязательно.

Репозиторий и его актуальный `main` являются источником истины. Сжатый диалог используется только как дополнительный контекст.

## Рабочая среда

Локальная рабочая среда проекта:

```text
Git Bash / MINGW64 (Windows 10)
```

Корень локального репозитория:

```text
~/projects/vunderkind
```

Обязательные правила:

- использовать только команды, совместимые с Git Bash;
- никогда не использовать PowerShell или cmd;
- каждый исполняемый блок начинать с явного `cd ~/projects/vunderkind &&`;
- не предполагать текущую директорию;
- использовать пути с `/`, совместимые с Git Bash;
- в Python-скриптах всегда указывать `encoding='utf-8'` при чтении и записи файлов.

## Разделение команд и безопасность

В интерактивных блоках запрещено:

- использовать `set -e`, `set -E`, `set -u` или `set -o pipefail`;
- использовать `exit` или `exit 1`;
- оставлять потенциально неуспешные команды без `if ... then ... fi`, `&&` или `|| true`;
- допускать закрытие Git Bash из-за ненулевого кода отдельной команды.

Цепочки команд строить через `&&`. Критичные шаги оборачивать в `if ... then ... else ... fi`.

Длинные или сложные правки файлов выполнять через `python3 -c` с явным `encoding='utf-8'`, а не через sed или awk.

Файлы создаются через `cat > file << 'EOF'` (heredoc с кавычками для предотвращения подстановки переменных). Простые дописывания через `cat >>`.

## Существующие ресурсы

Перед созданием файла или архитектурного решения необходимо проверить, нет ли уже подходящего ресурса в репозитории.

Запрещено:

- придумывать имена существующих файлов;
- предполагать наличие файлов без проверки;
- создавать дубликат уже существующего ресурса;
- заново проектировать то, что уже зафиксировано в документации.

## Факты и предположения

Нельзя выдавать предположение за подтверждённый факт.

Необходимо:

- явно отделять подтверждённые данные от предварительных;
- не выдумывать информацию, которую нельзя подтвердить на старом сайте, сайте франшизы, в PDF или в сообщениях заказчицы;
- не использовать имена тренеров на сайте (бренд «Школа Васильевой», но отзывы не редактируем);
- не использовать формы обратной связи (152-ФЗ);
- не использовать штампы типа «Знакомо?»;
- не сокращать отзывы — заказчица хочет полные тексты.

## Порядок работы с Git

Перед изменениями необходимо проверить:

- текущий `HEAD` (через GitHub API или `git log --oneline -3`);
- состояние рабочего дерева (`git status --short`);
- фактическое содержимое изменяемых файлов.

Изменения должны быть:

- минимальными;
- логически связанными;
- проверяемыми;
- без приватных данных и секретов.

Перед коммитом показать:

```text
git status --short
git diff --check
git diff --stat
```

Коммит должен быть коротким и соответствовать одному логическому изменению. Формат сообщений: `feat:`, `fix:`, `perf:`, `docs:`.

Не выполнять amend, rebase, force push или удаление истории без прямого указания пользователя.

PROGRESS.md обновляется в конце каждой фазы.

## Технические ограничения

- GitHub Pages: `Cache-Control max-age=600` — изменить нельзя.
- Метрика всегда в конце `<body>` — не в `<head>` (Performance).
- SVG-иконки имеют свои цвета — не переопределять в CSS.
- Контент меняет только разработчик — заказчица сама не редактирует.
- Lighthouse 73 по Performance — допустимо, не портить код ради цифры.
- silachtenia.ru — конкурент, не партнёр.

## Коммуникация

Не задавать лишние вопросы, если ответ уже есть в документации. Не перекладывать следующий шаг на пользователя, когда мяч на стороне агента.
